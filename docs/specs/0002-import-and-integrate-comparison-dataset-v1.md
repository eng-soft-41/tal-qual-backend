# Import and Integrate Comparison Dataset v1

## Goal

Import the generated `tal-qual` comparison dataset `v1` into MongoDB and expose
it through the `/comparisons` API as the canonical backend dataset for frontend
visualization, review, and audit workflows.

This spec builds on `0001-comparison-dataset-api.md`. The first spec defined the
target API and import shape. This spec pins the actual generated export contract,
manifest counts, importer behavior, API semantics, and verification steps needed
to fully integrate the dataset.

## Source Dataset

The dataset is generated by the sibling `tal-qual` data project.

Backend export path, relative to this backend project:

```text
../tal-qual/data/export/backend/comparisons/v1/
```

Equivalent path inside the data project:

```text
data/export/backend/comparisons/v1/
```

Source extraction:

```text
data/gold/como_article_ground_vehicle_candidates
notebooks/01_full_como_article_ground_vehicle_mvp.ipynb
```

The backend must not read Spark Parquet, notebooks, or Spark `part-*`
directories. It consumes only the backend export files listed below.

## Required Files

The importer must fail fast if any required file is missing:

```text
candidates.jsonl
ground_vehicle_counts.json
vehicle_ground_counts.json
ground_counts.json
vehicle_counts.json
examples.jsonl
manifest.json
```

Debug and review files may exist but are not required for the first public API
integration:

```text
review_sample.jsonl
rejected_or_review_candidates.jsonl
```

## Manifest Contract

The generated `manifest.json` is the export integrity source. The importer must
persist it in `comparison_manifests` with:

```text
dataset_version = "v1"
importedAt
```

The current generated manifest summary is:

```text
dataset_name: tal-qual-comparisons
dataset_version: v1
pattern_type: como_article_ground_vehicle
schema_version: 1
candidate_count: 2136
visualization_ready_count: 2133
ground_count: 40
vehicle_count: 742
ground_vehicle_pair_count: 940
generated_at: 2026-05-17T20:06:34.645298+00:00
```

The importer must validate imported counts against these manifest fields:

```text
candidate_count -> candidates.jsonl rows
ground_count -> ground_counts.json rows
vehicle_count -> vehicle_counts.json rows
ground_vehicle_pair_count -> ground_vehicle_counts.json rows
```

The importer should also validate `visualization_ready_count` against the number
of imported candidates where `visualization_ready = true`.

If `examples.jsonl` and `vehicle_ground_counts.json` have explicit manifest
count fields in a future export, the importer should validate those fields too.

## Import Command

Use this command from the backend project:

```text
npm run import:comparisons -- ../tal-qual/data/export/backend/comparisons/v1
```

Importer behavior:

1. Resolve the export directory from the command argument.
2. Load and validate `manifest.json`.
3. Derive `dataset_version` from `manifest.dataset_version`, defaulting only if
   the manifest omits it.
4. Reject imports whose `dataset_version` is not `v1` unless the command
   explicitly allows another version in the future.
5. Load required JSON and JSONL files.
6. Validate candidates with the `ComparisonCandidate` schema.
7. Upsert candidates by `{ dataset_version, candidate_id }`.
8. Replace aggregate/example collections for the imported `dataset_version`.
9. Persist the manifest after successful file validation.
10. Create or update required indexes.
11. Print a structured import summary.
12. Exit non-zero on missing files, invalid JSON, validation failures, MongoDB
    failures, or manifest count mismatches.

The printed summary should include at least:

```text
dataset_version
candidate_count
visualization_ready_count
ground_count
vehicle_count
ground_vehicle_pair_count
vehicle_ground_pair_count
example_count
importedAt
```

All imported documents must include:

Candidates preserve all row-level fields from `candidates.jsonl`.

Aggregate documents should expose stable query/display keys:

```text
comparison_ground_vehicle_counts:
  ground_lemma
  vehicle_head_clean_lemma
  count

comparison_vehicle_ground_counts:
  vehicle_head_clean_lemma
  ground_lemma
  count

  ground_lemma
  count

comparison_vehicle_counts:
  vehicle_head_clean_lemma
  count
```

If the JSON aggregate files are encoded as maps rather than arrays, the importer
must normalize them to the shapes above rather than storing opaque map keys.

## Display and Query Semantics

Use these dataset fields consistently:

```text
vehicle_text_clean
```

Default display text for a candidate vehicle phrase.

```text
vehicle_head_clean_lemma
```

Canonical vehicle aggregation key. Aggregate files are built from this cleaned
key, not from raw vehicle phrases.

```text
visualization_ready = true
```

Default public/queryable filter for pair and example views. The full candidate
set remains available for audit and review workflows.

## API Routes

The backend must expose these routes under `/comparisons`.

### `GET /comparisons/manifest`

Returns the active manifest, defaulting to the latest imported manifest.

Query:

```text
dataset_version?: string
```

### `GET /comparisons/pairs`

Returns ground -> vehicle pair counts.

Query:

```text
dataset_version?: string
ground?: string
vehicle?: string
limit?: number
offset?: number
visualization_ready?: boolean
```

Defaults:

```text
dataset_version = latest imported manifest
limit = 100
offset = 0
visualization_ready = true
```

Sort:

```text
count desc, ground_lemma asc, vehicle_head_clean_lemma asc
```

### `GET /comparisons/grounds`

Returns ground summary rows sorted by count descending.

Query:

```text
dataset_version?: string
limit?: number
offset?: number
```

Sort:

```text
count desc, ground_lemma asc
```

### `GET /comparisons/vehicles`

Returns vehicle summary rows sorted by count descending.

Query:

```text
dataset_version?: string
limit?: number
offset?: number
```

Sort:

```text
count desc, vehicle_head_clean_lemma asc
```

### `GET /comparisons/examples`

Returns candidate examples.

Query:

```text
dataset_version?: string
ground?: string
vehicle?: string
quality_label?: string
visualization_ready?: boolean
limit?: number
offset?: number
```

Defaults:

```text
dataset_version = latest imported manifest
limit = 100
offset = 0
visualization_ready = true
```

Sort:

```text
confidence desc, candidate_id asc
```

### `GET /comparisons/candidates/:candidateId`

Returns one candidate by id.

Query:

```text
dataset_version?: string
```

The route must return `404` when the candidate does not exist for the resolved
dataset version.

## Response Shape

All list routes must return:

```json
{
  "data": [],
  "meta": {
    "dataset_version": "v1",
    "limit": 100,
    "offset": 0,
    "total": 2136
  }
}
```

Single-resource routes must return:

```json
{
  "data": {}
}
```

Error responses should keep the existing backend shape:

```json
{
  "message": "Validation error"
}
```

## Frontend Integration Contract

The current frontend mock dataset is not the backend contract. It is a product
fixture for the first visualization pass. The backend should expose stable raw
and aggregate data; the frontend should adapt its local data module to the API
response shape when this backend work is complete.

The backend API must be sufficient for these frontend views:

```text
dataset summary:
  /comparisons/manifest

ground cards and concentration chart:
  /comparisons/grounds
  /comparisons/pairs?ground=<ground_lemma>

vehicle scatter plot:
  /comparisons/vehicles

case studies by vehicle:
  /comparisons/pairs?vehicle=<vehicle_head_clean_lemma>
  /comparisons/examples?vehicle=<vehicle_head_clean_lemma>

example carousel:
  /comparisons/examples?visualization_ready=true
```

The frontend may derive these display fields from backend responses instead of
requiring them as stored backend fields:

```text
distinct_vehicle_count
top_vehicle_head_clean_lemma
top_vehicle_count
top_vehicle_share
distinct_ground_count
top_ground_lemma
top_ground_count
top_ground_share
```

`example_candidate_ids` is also a frontend fixture convenience, not a required
backend field. Frontend integration should fetch examples through
`/comparisons/examples` filtered by `ground` and/or `vehicle` when examples are
needed for a displayed pair or case study.

The frontend data adapter should normalize backend list responses from:

```json
{
  "data": [],
  "meta": {
    "dataset_version": "v1",
    "limit": 100,
    "offset": 0,
    "total": 2136
  }
}
```

into the component-facing arrays currently returned by the mock data module.
This keeps component changes small while making the API response metadata
available for pagination, audit views, and dataset freshness indicators.

## Verification

After implementation, verify:

1. `npm run build` passes.
2. Import succeeds with:

   ```text
   npm run import:comparisons -- ../tal-qual/data/export/backend/comparisons/v1
   ```

3. Import summary matches the manifest:

   ```text
   candidate_count = 2136
   visualization_ready_count = 2133
   ground_count = 40
   vehicle_count = 742
   ground_vehicle_pair_count = 940
   ```

4. `/comparisons/manifest` returns dataset version `v1`.
5. `/comparisons/pairs` defaults to `visualization_ready = true`.
6. `/comparisons/grounds` returns `40` total rows for `v1`.
7. `/comparisons/vehicles` returns `742` total rows for `v1`.
8. `/comparisons/candidates/:candidateId` can fetch a known imported candidate.
9. Invalid query parameters return `400` through the existing Zod error handler.

## Open Implementation Notes

The current API scaffolding should be tightened against this spec:

```text
manifest count keys
dataset_version should come from manifest
aggregate map normalization should produce stable field names
default visualization_ready filtering should match the exported aggregate shape
indexes should include manifests, examples, and vehicle_ground_counts
route sorts should include deterministic secondary keys
```

These are implementation tasks, not data-project tasks.
